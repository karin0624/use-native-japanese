# 開発の進め方

## 要求の確定

このスキルは主担当が開発を進めるための手順である。主担当は[AGENTS.md](../../../AGENTS.md)の原則全体に従い、工程と担当を定め、実施担当には担当工程の手順を渡す。実施担当もAGENTS.mdを読み、担当作業に適用される原則全体を守る。原則の一部だけを選ぶ根拠にしない。

独立レビューでは、主担当が対象と時点を定め、[レビュワー定義](../../../.codex/agents/reviewer.toml)に基づいて評価を依頼する。レビュワーは開発を進める担当ではなく、評価結果を返す担当である。工程を進める判断、修正担当への差し戻し、再レビューの呼び出し、完了・公開の判断と実行は主担当が担う。

- ユーザーの原指示と有効な訂正から目的・対象・完了条件を確定する。参考例・仮説を採用指示へ変えない。
- 既存コード・テスト・文書・Issueは検証対象である。記述の存在を仕様の正当性にせず、要求と技術的根拠へ戻って採否を決める。
- 指摘への対応でも元の目的と有効な制約を保持する。既知の未達を「制約」へ書き換えて完了条件を縮めない。

## 保存先

| 内容 | 保存先 |
| --- | --- |
| 一つの問題・受入条件 | [Issueテンプレート](../../../.github/ISSUE_TEMPLATE/task.md)に従うIssue本文 |
| 判断に必要な調査・設計・実験・検証の結果 | 同じIssueの重要な共有または完了時のまとめ |
| 変更内容・検証・レビュー | 関連する一つのPR |
| 継続利用する操作・仕様・設計・研究知見 | [文書テンプレート](../../../docs/README.md)で定める場所 |
| 必要な生出力・一時コード | Git管理外の作業領域。共有が必要で公開可能な生出力だけをIssue添付またはCI artifactへ置く |

一時的な文書は、名前・拡張子・保存場所を問わず作らない。作業報告をファイルへ転記せず、共有が必要な結果を以下の時点でIssueへ集約する。

恒久文書は、継続利用する読者と用途が明確なものだけを残す。先行研究は課題・方式・知見・限界・一次資料を保持できる。進捗、試行順、単発測定、開発方針を混ぜない。不要・重複・容易に再構成でき用途がない情報は削る。変更履歴はGitへ委ね、作成日・更新日・履歴欄を設けない。研究の発表年や互換性に必要な版は内容として記す。

文書の書式はdocs、作業全体の原則は[AGENTS.md](../../../AGENTS.md)、開発の手順はこのスキルに一元化する。AGENTSやスキルの永続指示は、ユーザーが依頼した範囲で変更する。

## 共有する時点と内容

開発中の作業ログを継続投稿しない。途中で共有するのは、判断が必要な重大な発見、方針変更、外部対応が必要な事実がある場合だけにする。それ以外の結果は完了時にまとめる。工程・コマンド・小実験・一つの問いごとには投稿せず、操作の実況や単なる進捗報告を残さない。

共有時には結果・判断の根拠・検証・残課題を、読者の判断に必要な量で集約する。設計や実験の書式は内容を整理するために使い、工程ごとのコメント作成や、同じ内容のIssue・PRへの重複転載を求めない。途中の共有が必要でも、そのために独立して進められる作業を止めない。

公開先を問わず、[AGENTS.mdの公開規則](../../../AGENTS.md#公開する情報)を適用する。公開資料は指示・会話・内部委任文の記録にせず、必要な課題の目的・要件・結果へ書き直す。検証用の入力・出力・コマンド、添付、CI artifact、公開ログにも私的な指示や会話が含まれないことを確認する。

## 工程と成果物

テストの設計・追加・変更・レビューと検証の前に、[仕様からテストを作る手順](../../../docs/guide/testing.md)を読む。

主担当は原依頼に必要な工程と実施担当を定める。以下の成果は共有時に集約する内容であり、工程ごとの文書作成・Issue投稿を求めない。既知の根拠は対象版・条件への適用を確認して再利用する。判断を変える未解決事項がなければ実験を増やさず、変更に必要な確認だけを行う。適用すべき工程を、他の担当の作業やレビュー実施だけで済ませない。

### 1. 課題定義

- **担当・開始条件**：主担当が、依頼の開始時と対象・条件の変更時に行う。
- **作業・成果**：原要求と有効な訂正を読み、現状との差、対象・対象外、観測可能な受入条件、許可された操作を確定する。同じ問題のIssueへ対応付け、既存の記録を再利用する。
- **次へ進む条件**：目的と完了証拠を説明できれば2へ進む。調査・文書のみの依頼は、その成果を完了条件とし、未依頼の実装やIssue終了へ拡張しない。操作の可否は有効な依頼と既存の許可に従う。
- **不成立時**：原要求と現状の確認へ戻る。自分で調査できる事実は調べ、必要な要求・権限が未確定な部分だけユーザーへ確認する。

### 2. 調査・設計

- **担当・開始条件**：主担当または指定した調査担当が、1の受入条件に対し、方式や原因の判断が必要なときに行う。
- **作業・成果**：下記「調査・設計」に従い、契約、実行経路、候補、採用・棄却の根拠、未確定点を調べる。依存の採否に限らず、設計全体をAGENTS.mdの原則へ照合する。成果は判断と根拠である。
- **次へ進む条件**：資料で判断できない仮説があれば3へ進む。実装の設計を確定する前に「独立レビュー」を行い、必要な修正と確認を終えてから4へ進む。調査だけで要求を満たす場合は独立レビュー後に6へ進む。
- **不成立時**：要求の不足は1、根拠の不足は2の追加調査、実測が必要な点は3へ戻す。方式を先に確定しない。

### 3. 限定実験

- **担当・開始条件**：主担当が指定した実施担当が、2で判断を変える未解決の仮説と、資料だけでは決まらない理由を特定したときに行う。
- **作業・成果**：下記「実験・検証」に従い、問い、条件、期待、観測、判定を定める。必要最小限の実験で支持・反証・未確定を分け、判断に使える結果を得る。
- **次へ進む条件**：結果を2へ戻して設計と採否を更新し、設計確定前の独立レビューへ進める。実験成功だけで設計を確定しない。
- **不成立時**：条件や観測の不足は必要箇所だけを直して3、仮説の反証や資料不足は2へ戻る。調査と実験を循環させ、不要な実験を反復しない。

### 4. 実装・文書作成

- **担当・開始条件**：指定した実施担当が、要求された変更の範囲と根拠が定まり、設計が必要な変更では設計確定前の独立レビューを終えたときに行う。実装担当は下記「実装の分担」に従う。
- **作業・成果**：根拠に対応する最小の差分と、必要な回帰テスト・恒久文書を作る。文書だけの依頼では指定した文書を成果とし、アプリケーションの実装を追加しない。
- **次へ進む条件**：選んだ方式と要求を具体的な差分へ反映できれば5へ進む。
- **不成立時**：実装上の不足は4、方式・根拠の問題は2、要求の不足は1へ戻る。未検証の補正や抽象を足して回避しない。

### 5. 検証・独立レビュー

- **担当・開始条件**：4の差分ができたら、主担当が実施担当に必要な検証を行わせ、対象版と検証結果がそろった時点で独立レビューを呼び出す。
- **作業・成果**：実施担当は受入条件から選んだ検査を実行し、元の利用経路と関係する退行を確認する。文書変更では内容・リンク・指示間の整合など必要な確認を行う。主担当はコード・テスト・文書と確認結果を「独立レビュー」の手順で渡し、対象版に対応する評価結果を受け取る。
- **次へ進む条件**：主担当は受入条件ごとの証拠、要修正事項の解消、完了判定に必要な未確認事項の有無を照合し、条件が満たされれば6へ進む。調査・文書だけの成果にも完了前の独立レビューを適用する。
- **不成立時**：主担当が実装・文書の問題を4、期待・設計・根拠の問題を2、要求の不足を1の担当へ戻す。修正後は影響する確認を行わせ、再レビューを呼び出す。

### 6. 整理・完了

- **担当・開始条件**：主担当が、依頼に適用される作成・検証・独立レビューの条件が満たされた後に行う。
- **作業・成果**：原依頼と有効な訂正を成果・証拠へ照合する。必要な恒久文書と参照を整え、「共有する時点と内容」「Issue・PR・公開」に従って公開可能な結果を集約する。公開操作を行う場合は、有効な依頼と既存の許可に従い、公開対象と方法も独立レビューで確認する。
- **次へ進む条件**：要求された成果を渡し、有効な依頼と既存の許可に基づく操作・必要な確認を終えたら完了とする。既存許可内のPR作成・mergeなどに追加の依頼や再確認を求めない。調査だけの依頼を未依頼の実装やIssue終了へ拡張しない。
- **不成立時**：不足する成果・根拠・確認を担当工程へ戻す。公開操作の具体的な阻害があれば、その操作と再開条件を示し、独立して続けられる作業を進める。

### 作業を終了する条件

説明・進捗報告・認識や方針の訂正・subagentの部分成果だけで、未完了の作業を終了することを禁止する。ユーザーの指摘には途中で回答し、元の依頼と有効な訂正に従って、その場で次の許可済み操作を続ける。「続けて」という再指示を待たない。

終了前に、原依頼の完了証拠・残作業・次に実行可能な操作を照合する。完了、ユーザーによる明示的な停止、または全ての続行可能な経路を妨げる具体的な阻害要因がある場合だけ応答を終了する。阻害要因がある場合は未完了であること、阻害された操作、必要な情報・権限・外部処理を示す。自分の仮説が崩れたことや設計が未確定であることは、調査を止める理由にしない。

## 調査・設計

[製品の目的と現在の実装範囲](../../../README.md)を区別する。各解析機の設計では、[共通の解析契約](../../../docs/design/usage.md#共通の解析契約)を確認する。[現在の照合条件](../../../docs/design/usage.md#現在の照合条件)は開発途中の述語解析機の方式であり、追加する解析機や構文条件による用例共用の検討を、その方式へ固定しない。開発計画・受入条件・未確定事項は[ロードマップ #38](https://github.com/karin0624/use-native-japanese/issues/38)を参照する。

共有する設計の判断と根拠は、必要な項目を次の順に整理する。

1. **問題**：どの受入条件を満たすか。
2. **契約**：必要な処理、入出力、保持情報、不変条件、失敗時の扱い。
3. **根拠**：公開可能な入力・対象版・公式仕様・コード・研究。観測と原因仮説を区別する。
4. **比較**：候補ごとの機能適合、必須依存、接続条件、品質、保守、時間・容量・更新費用。
5. **判断**：採用案と棄却理由。未確定点と、その確認結果で変わる判断。

目的→必要機能→実現原理→部品の順で選ぶ。ライブラリの出力を要件にせず、学習や交換を先に決めない。公式APIだけでは不足が分からない場合、関連issue・実装・利用例・論文も調べる。

原入力から処理段階ごとの入出力を追い、最初の不一致を原因候補にする。公式規約上の妥当な解析、接続の情報損失、比較設計の不備、資料不足を区別し、原因を裏付けてから対策を決める。

必要機能を保ちながらライブラリを極力減らす。必須依存と追加した処理系を分け、モデル・辞書・間接依存も費用へ含める。既存技術の組合せ・拡張を検討し、削減分を独自の日本語構文・活用・助詞規則やコード複製で補わない。

部品は保守状況・実利用・互換性を確認して選ぶ。スター数を利用者数、公開日を継続保守の証拠としない。技術資料で決まる事実をユーザーの好みに転嫁せず、要求・範囲・必要な合意が変わる箇所だけ相談する。

## 実験・検証

共有する実験・検証結果は、必要な項目を以下の書式で整理する。複数の確認をまとめ、共有時点は「共有する時点と内容」に従う。

```markdown
### 問い
この確認で決めること。

### 条件
commit、関係する依存版、入力、実行コマンド。

### 期待
要求または設計から導く結果。

### 観測
実結果。解釈とは分ける。

### 判定と次の操作
支持・反証・未確定、その理由、続ける操作。
```

判断に必要な公開可能な最小入力・期待・実結果・条件・結論をまとめの本文へ残す。消失するローカルパスや期限付きartifactだけを証拠にしない。私的な指示や会話に由来する入力は、検証に使った場合も公開せず、公開可能な代替例で確認する。代替例の結果を元の入力での検証と称さず、確認できた範囲と残る未確認事項を明示する。公開できない本文・認証情報は添付しない。

## 実装の分担

実装はユーザー指定のGPT-6.1 sol subagentへ渡し、effortを難易度に合わせる。目的・対象・根拠・次の操作・終了条件を渡す。主担当は担当の部分成果だけで完了にせず、必要な検証・独立レビュー・整理まで進める。

## 独立レビュー

### 実施する時点と担当

主担当は設計を確定する前、実装・検証後、調査・文書だけの依頼を完了する前に独立レビューを呼び出す。同じ成果・条件に対するレビューで複数の時点の要件を満たせる場合は重複させない。変更によって判断の前提や成果が変わった場合は、影響する範囲の再レビューを呼び出す。

主担当が、今回の判断・調査・作成に参加していない新しいagentを[レビュワー定義](../../../.codex/agents/reviewer.toml)に従って起動する。fresh contextを用意する責任は主担当にある。親の会話履歴・作業推論を自動継承させず、起動APIにcontext継承の指定がある場合は無継承を指定する。`spawn_agent`では`fork_turns="none"`を指定する。

既存の実施・調査agentの再利用や、会話履歴を保持したagentへの再考の指示を独立レビューに数えない。主担当のセルフチェックや、実施担当による自分の成果の確認も独立レビューに数えない。

### 渡す情報と受け取る結果

主担当は、無継承で起動するレビュワーが原要求と有効な訂正を直接読めるよう、レビュー用入力を用意する。レビュワー定義、対象版・差分・今回の判定対象、AGENTS.mdと関係する指示、参照可能な一次資料・確認結果を渡す。原要求へのアクセスが不足している場合は主担当が補い、自分の要約だけで代用しない。主担当の結論は確認対象として示し、正しいという前提を置かせない。私的な指示・会話・内部委任文を公開記録へ転載しない。

開発スキル全体をレビュワーの実行手順として渡さない。手順への適合やワークフロー文書自体が判定対象なら、該当箇所を評価資料として渡す。工程を評価することと、その工程をレビュワーに実施させることを区別する。実施担当に必要な調査・検証を、レビューへ移譲して省略しない。

主担当は、レビュワー定義に基づく評価結果として、対象版と確認範囲、指摘と根拠、必要な修正・確認、未確認事項、総合評価を受け取る。レビュー観点と評価方法はレビュワー定義へ集約する。

### 判定と修正の循環

主担当は、受け取った評価結果を対象版と照合し、指摘がないことと、必要な確認ができていないことを区別する。対象・理由・必要な確認が不明な場合はレビュワーへ不足を確認し、完了に必要な証拠の欠落を合格として扱わない。

主担当は指摘を該当工程の実施担当へ戻し、修正と影響する範囲の確認を行わせる。修正後の対象版・差分・確認結果・指摘への対応をそろえ、独立した再レビューを呼び出す。初回の独立レビューを行ったレビュワーへ戻してよく、変更の影響と指摘の解消を評価対象にする。元の作成担当が独立レビュー役を兼ねない。指摘の無視や、反証なしの却下を禁止する。採用しない場合は要求・一次資料・確認結果に基づく反証を渡し、レビュワーの再判定を受ける。主担当自身に適用される調査・設計・検証も省略しない。

主担当は再判定と完了に必要な証拠を照合して、次工程へ進むか、該当工程へ戻すかを判断する。レビュー結果だけで工程の実施や完了・公開の判断を代替しない。

## Issue・PR・公開

一つの問題を一つのIssue・PRへ対応させる。調査だけの依頼では、未依頼の実装や実装PRを追加しない。調査・計測・実装・レビュー修正は内部工程であり、別の課題へ分割しない。別々に受け入れ可能な問題は分けるが、同じ原因だと未確認の課題を無理に統合しない。

Issue本文は課題定義、コメントは重要な共有と完了時の判断・証拠のまとめに使う。変更時は未解決・修正済み・未確認を区別する。統合時は再現入力と未達条件を移し、閉じる側に統合先と理由を残す。

PR本文は問題、変更後の挙動、検証、関連Issueを簡潔に記す。公開前に本文・コメント・コミットメッセージ・差分・追跡対象・添付・公開ログと帰属を確認し、指示・会話・内部委任文、その抜粋・翻訳・再構成・スクリーンショット、私的な指示由来の検証入力、原コーパス本文・構築用正本・認証情報を含めない。既存の転載を削除する場合は、本文だけでなく編集履歴・引用先・添付の残存も確認する。利用できる操作で消せない範囲は削除済みと報告せず、残件として示す。固定モデル・配布参照は既存LFS管理を維持する。

このプロジェクトでは検証後のpush・PR mergeまで許可されている。npm registryへの公開は行わない。
