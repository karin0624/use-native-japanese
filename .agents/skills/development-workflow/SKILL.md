# 開発の進め方

## 要求の確定

- ユーザーの原指示と有効な訂正から目的・対象・完了条件を確定する。参考例・仮説を採用指示へ変えない。
- 既存コード・テスト・文書・Issueは検証対象である。記述の存在を仕様の正当性にせず、要求と技術的根拠へ戻って採否を決める。
- 指摘への対応でも元の目的と有効な制約を保持する。既知の未達を「制約」へ書き換えて完了条件を縮めない。

## 保存先

| 内容 | 保存先 |
| --- | --- |
| 一つの問題・受入条件 | [Issueテンプレート](../../../.github/ISSUE_TEMPLATE/task.md)に従うIssue本文 |
| 設計案・調査・実験・検証・判断 | 同じIssueのコメント |
| 変更内容・検証・レビュー | 関連する一つのPR |
| 継続利用する操作・仕様・設計・研究知見 | [文書テンプレート](../../../docs/README.md)で定める場所 |
| 必要な生出力・一時コード | Git管理外の作業領域。共有が必要な生出力はIssue添付またはCI artifact |

一時的な文書は、名前・拡張子・保存場所を問わず作らない。作業報告をファイルへ転記せず、Issueへ記録する。

恒久文書は、継続利用する読者と用途が明確なものだけを残す。先行研究は課題・方式・知見・限界・一次資料を保持できる。進捗、試行順、単発測定、開発方針を混ぜない。不要・重複・容易に再構成でき用途がない情報は削る。変更履歴はGitへ委ね、作成日・更新日・履歴欄を設けない。研究の発表年や互換性に必要な版は内容として記す。

文書の書式はdocs、文章の簡潔さはAGENTS、開発方針はこのスキルに一元化する。AGENTSやスキルの永続指示は、ユーザーが依頼した範囲で変更する。

## 工程と成果物

| 工程 | 作業 | 成果物 | 次へ進む条件 |
| --- | --- | --- | --- |
| 1. 課題定義 | 原要求と現状の差を特定 | Issue本文 | 対象と観測可能な受入条件が明確 |
| 2. 調査・設計 | 必要機能と契約を定義し、方式・部品を比較 | 設計コメント | 採用理由と未確定点を説明可能 |
| 3. 限定実験 | 資料では決まらない仮説を確認 | 実験コメント | 支持・反証・未確定と次の操作が確定 |
| 4. 実装 | 根拠に対応する変更と回帰テスト | コード差分 | 選んだ方式を実行可能 |
| 5. 検証・レビュー | 元の利用経路と関連する退行を確認 | 検証コメント・レビュー | 各受入条件の証拠があり必須修正なし |
| 6. 整理・完了 | 必要な恒久文書とリンクを更新 | PR・完了したIssue | 原依頼との照合と公開前確認が完了 |

原因・設計が既知なら根拠を使い、不要な調査・実験を省く。調査が目的の依頼は判断と根拠が成果となる。実装依頼を設計コメントや起票だけで終了せず、許可済みの次工程まで継続する。

## 調査・設計

設計コメントは次の順に記す。

1. **問題**：どの受入条件を満たすか。
2. **契約**：必要な処理、入出力、保持情報、不変条件、失敗時の扱い。
3. **根拠**：原入力・対象版・公式仕様・コード・研究。観測と原因仮説を区別する。
4. **比較**：候補ごとの機能適合、必須依存、接続条件、品質、保守、時間・容量・更新費用。
5. **判断**：採用案と棄却理由。未確定点と、その確認結果で変わる判断。

目的→必要機能→実現原理→部品の順で選ぶ。ライブラリの出力を要件にせず、学習や交換を先に決めない。公式APIだけでは不足が分からない場合、関連issue・実装・利用例・論文も調べる。

原入力から処理段階ごとの入出力を追い、最初の不一致を原因候補にする。公式規約上の妥当な解析、接続の情報損失、比較設計の不備、資料不足を区別し、原因を裏付けてから対策を決める。

必要機能を保ちながらライブラリを極力減らす。必須依存と追加した処理系を分け、モデル・辞書・間接依存も費用へ含める。既存技術の組合せ・拡張を検討し、削減分を独自の日本語構文・活用・助詞規則やコード複製で補わない。

部品は保守状況・実利用・互換性を確認して選ぶ。スター数を利用者数、公開日を継続保守の証拠としない。技術資料で決まる事実をユーザーの好みに転嫁せず、要求・範囲・必要な合意が変わる箇所だけ相談する。

## 実験・検証

コメントの書式は以下とする。一つの問いの結果が出た単位で記録し、操作の実況は残さない。

```markdown
### 問い
この確認で決めること。

### 条件
commit、関係する依存版、入力、実行コマンド。

### 期待
要求または設計から導く結果。

### 観測
実結果。解釈とは分ける。

### 判定と次の操作
支持・反証・未確定、その理由、続ける操作。
```

判断に必要な最小入力・期待・実結果・条件・結論はコメント本文へ残す。消失するローカルパスや期限付きartifactだけを証拠にしない。公開できない本文・認証情報は添付しない。

解析値の転記一致、テスト・CI成功、誤用指摘の妥当性は別々に評価する。対象言語・課題・評価単位が違う研究成績を転用しない。情報追加の評価は入力・境界・条件を固定し、評価文の参照登録を改善に数えない。

## 実装・レビュー

- 実装はユーザー指定のGPT-6.1 sol subagentへ渡し、effortを難易度に合わせる。目的・対象・根拠・次の操作・終了条件を渡す。
- 振る舞いの回帰を既存の試験へ加える。実装の写し、些細な記述の固定、個別文書だけの専用CIを増やさない。
- 実装後はfresh contextのsubagentが、原要求・設計前提・単純さ・保守性・テストの妥当性を確認する。
- 検証コマンドは[開発手順](../../../docs/guide/development.md)を使う。変更に必要な確認を選び、無変更の条件で反復しない。

## Issue・PR・公開

一つの問題を一つのIssue・PRへ対応させる。調査・計測・実装・レビュー修正は内部工程であり、別の課題へ分割しない。別々に受け入れ可能な問題は分けるが、同じ原因だと未確認の課題を無理に統合しない。

Issue本文は課題定義、コメントは判断と証拠に使う。変更時は未解決・修正済み・未確認を区別する。統合時は再現入力と未達条件を移し、閉じる側に統合先と理由を残す。

PR本文は問題、変更後の挙動、検証、関連Issueを簡潔に記す。公開前に差分・追跡対象・帰属を確認し、原コーパス本文・構築用正本・認証情報を含めない。固定モデル・配布参照は既存LFS管理を維持する。

このプロジェクトでは検証後のpush・PR mergeまで許可されている。npm registryへの公開は行わない。
