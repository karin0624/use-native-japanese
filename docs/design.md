# 現在の設計

## 目的と完成条件

AIが出した誤った日本語をリアルタイムで位置付き指摘し、可能なら訂正案を出す。「重複を畳む」のような、用例に裏付けられない語の使い方を中心に、スクリプトとtextlintから利用できるようにする。将来の商用利用を考慮する。

今回の完成条件は、定めた形式の情報追加で役立つ範囲を改善でき、容量・構築・検索費用を現実的に増やせる試作を示すことである。全件正答、全用例の収録、全複合語の厳密な同定は求めない。訂正案は未実装である。

Issue #15では、語彙の欠落を生む句取得と、解析後の識別子投影を変更する。現行契約はv10であり、同じ6,463本文での再構築と限定評価を完了した。[v10の検証](projection-validation.md)に測定条件と結果を記す。最終資源での製品経路とレビューは確認済みである。対応3OSの導入・実行は[PRのCI](../.github/workflows/npm-package.yml)で検査し、その実行結果を参照する。

## 対象

検査するのは、原文の述語側の語彙Pと名詞側の語彙Nが、どの関係で使われたかである。役割と品詞を分け、サ変名詞等の語彙内容も保持する。名詞内部の構成だけを独立した使い方として指摘しない。

現試作は、GiNZAが公開する元の`nsubj`・`obj`・`iobj`・`obl`と`acl`・`amod`の文節間関係を対象にする。前四者では従属側がN、元headがP、後二者では被修飾側がN、修飾側がPとなる。元のUPOS・依存ラベル・向きを保持し、他の辺を品詞だけで対象へ変換しない。名詞側が既存辞書の詳細品詞「助動詞語幹」に属する機能カテゴリは、従来どおり対象から除く。この対象選択が全ての語彙誤用に十分だとは主張しない。

正用同士の意味差、文章のもっともらしさ、AI生成判定、分野ごとの文体の適否は対象外である。原解析の正誤が未確定な例を、想定する日本語と違うだけで誤解析と決めない。旧監査210件を期待する品詞・辺との差から「誤解析確定」とした認定は撤回し、正解注釈として使わない。文書上の分類変更で実際の不備を解消したとは扱わない。

## 同一視する条件と支持

入力と参照に同じ正規化`ginza-bunsetu-functional-projection-v10`を適用する。

1. ASCIIの連続英数字wordrunと、従来の英字/_開始の記号を含む識別子profileを分ける。元token境界にstrictに一致する複数tokenだけを、spaCyの公開retokenizerで依存解析前に一tokenへ結合する。一tokenの公開lemmaは保持し、数字開始の記号結合は増やさない。その同じDocを解析・照合し、解析後に名前全体へ投影しない。識別子内部の分割語で予測した辺を後から名前へ付け替えない。
2. 各元P/N anchorの所属文節から、GiNZAの位置分類`FUNC`・`SYN_HEAD`または公開依存関係`aux`・`case`・`cop`に該当するTokenと、それらをheadとする文節内の`fixed`直接子を除く。`CONT`は位置分類であり、独立した語彙分類とはみなさない。`mark`・`cc`等を依存ラベルだけで追加除外しない。さらに公開`is_punct`・`is_space`だけを非語彙として除き、残りの公開lemmaと原文との対応を原文順に全て保持する。表示は選択Tokenの先頭から末尾までの包絡一範囲とし、途中の非選択語を比較lemmaへ加えない。`NO_HEAD`を独自に機能語とみなさない。元anchorが除外される場合、同文節の別の語で関係を作らない。
3. 照合条件はPのlemma列・元UPOS、元依存ラベル、Nのlemma列・元UPOS、Nの元方向とする。Pを近義語へ置き換えず、入力と用例の条件差を暗黙に統合しない。

この語彙列は完全な語彙IDではない。同文節の修飾等も条件に残す保守的な比較であり、共有できる用例を分断する場合がある。主辞句APIが選んだTokenを語全体とみなす旧方式から、必要な語彙成分を落とさないことを優先して改める。元の辺・UPOS・向きの正しさを修復する方式でもない。

支持は次の二経路で調べる。いずれも支持がなければ、書き手へ通常の`error`を返す。

- **直接支持**：同じ条件の用例集合をBloomで照合する。陽性の`indexed`には低確率の誤通過があり、個別の実用例を確認済みという意味ではない。
- **名詞一般化による支持**：P・両端の元UPOS・依存ラベル・Nの方向を固定し、同じ群の異なる名詞列を等票とする。既存の圧縮fastTextで合成した入力名詞ベクトルと、用例名詞群の平均方向のcosineが0.35以上なら`supported`とする。一般化するのはNだけである。

群平均と0.35は、限定的な成立例と費用から残す再検証仮説であり、目的から必然の定数ではない。名詞の話題的な近さ、複合語の成分平均、多峰性を十分に扱える保証はない。用例追加で平均方向が変わり、既存判定が悪化する場合もある。直接支持の改善を、名詞一般化全般の有効性とは呼ばない。

製品の結果は、支持ありで無出力、支持なしで位置付き`error`、解析・資源破損・不正な数値等の処理異常で`systemerror`の三つだけとする。ベクトルや比較群がなければ一般化による追加支持なしとし、類似度0を捏造しない。未収録は日本語全体での不存在の証明ではなく、辞書不足`warn`や第四の保留状態は設けない。

## 必要な機能と既存部品

| 必要な機能 | 採用する部品・接続 |
| --- | --- |
| 本文と原文位置の対応 | 元Docの各Token位置、Pythonの文字添字、JSONLのUTF-16変換、textlintの位置対応 |
| 語境界・品詞・lemma・依存関係 | 軽量`ja_ginza`、GiNZAと必須依存のspaCy・SudachiPy・SudachiDict-core。NERは使わない |
| 識別子境界の事前確定 | 既存のASCII profileと`Doc.char_span`のstrict境界、公開retokenizer |
| 比較語彙と元関係の取得 | GiNZAの公開文節・機能分類・`fixed`と元依存出力。新しい日本語規則・語別例外を加えない |
| 用例支持 | 既存の出典付きJSONL・正本SQLite、Bloom、名詞群平均、圧縮fastText |
| 反復検査と配布 | 解析器・参照を再利用する`Inspector`/JSONL worker、npmのtextlintルール |

GiNZAとその必須依存の構成は維持する。ライブラリ数を減らすための解析器置換は行わない。採用理由は、既存の公開出力から必要な語彙・関係・位置を取り出せ、独自の日本語解析を重ねずに済むことである。機能表現の構成は公開`Token.children`の`fixed`直接子から読み取れるため、当方forkの追加句APIは不要となった。必要情報が公式公開出力だけで得られることを理由に、公式GiNZA 5.3.0を使い、vendor wheel・patchを撤去した。ライブラリ数の数合わせを目的とした変更ではない。

構築用正本には組合せと出典・出現の対応を残す。配布は直接集合のBloomと群平均・件数・契約情報とし、全用例の個別ベクトルや原コーパス本文を配らない。固定モデルと配布参照はGit LFSで管理し、npm配布物へ実体を同梱する。

異なる比較条件数N、群数G、次元d、文字列量L、Bloom誤認率pに対し、配布の保存量は`O(N log(1/p) + Gd + L)`である。固定pで件数等に比例するが、本文量に対するN・G・語彙長の増加、SQLiteの管理領域、解析・全量再compile・照会費用も別に確認する。現在の配布容量だけで拡張可能とは判断しない。

## 検証と残る限界

新規用例を加えず、既存1,025記事・6,463本文をv10で再構築した。基底Bと既存8本文Dの比較では136用法・22群が増え、別記事の「世界的／大ヒット」への位置付き指摘が消えた。新参照は89,964,544 bytes、固定モデルは21,944,687 bytes。評価入力を参照へ登録せず、名詞一般化と境界0.35も固定した。

核心43本文・既知5診断では、教師2対の訂正側にも指摘が残り、原語取得不足4件、ぼうし／帽子の表記比較と入力ベクトル不能を区別した。全遷移、保存Doc再利用の条件、入力hash・出典ID・構築費用は[検証記録](projection-validation.md)を参照する。Python135＋19 subtests、Node24とRuffは通過し、fresh contextのv10レビューは指摘0件。最終資源でのcheckout・配布物・実textlint4呼出しも成功した。初回起動と常駐時の測定条件は検証記録に記す。対応3OSの導入・実行の結果は[PRのCI](../.github/workflows/npm-package.yml)で確認する。

語彙・関係の取得不備、比較条件の分断、資料未収録、Bloomの誤通過、一般化の誤支持は分けて記録する。文書更新や語彙取得件数の増減だけで完了にはしない。全語彙・全構文の正答、全入力でのリアルタイム性は未証明である。構築時間を検査端末の応答時間へ読み替えない。複数の関係を別々に照合した結果から、同じ参照出現での共同成立を保証することもできない。
