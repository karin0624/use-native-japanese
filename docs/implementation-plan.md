# 目的、設計、検証の順序

目的は、AIが出した誤った日本語をリアルタイムで位置付き指摘し、可能なら訂正案を出すこと。「重複を畳む」のような用例に裏付けられない語の使い方が中心であり、正用同士の意味差を識別する問題へ広げない。用例検索、構文解析、一般化は手段である。

## 現在の工程

**[全文の照合結果から、参照の意味情報を使える範囲を確認する](full-text-support-check.md#全文結果と次の限定調査)。** 中間保存を修正し、同じ4全文の365照会・支持計算・全318境界の集計を完了した。340関係中、直接支持142、連続支持153、計算不能45である。格解析不能の1文118字は別に保持した。旧対象の参考値付近でも通常本文の指摘範囲が広く、現時点で製品の境界を決める根拠は足りない。

原語を保つ低支持例「世界的な大ヒット」では、参照の別frameにある`<主体準>`を実語vectorへ変換できず比較していない。この項と`raw_semantics`が、観測例の抽象化・意味制約・既定値のどれに当たるかは未確認であり、正の用例とはまだ断定しない。次は、その生成と意味、入力の同じ名詞へ対応付ける既存の仕組み、そこから判断できる範囲だけを一次資料・固定source・関連研究とissueで調べる。対応可能なら必要な拡張と対照を設計し、不可能なら具体的な不足に対応する研究へ戻る。カテゴリの存在だけで通過させる変更や、特殊IDを実語として扱う変更は先行しない。

この不足を全ての低支持の説明にはしない。「ラベルが含まれます」は原語・受動・格を保持し、勝者の24単位全てを比較できても低支持だった。別語への解析、名詞の未収録、参照情報の未利用、比較方式の性質を区別して原因を確かめる。同じ対象の再採点は現段階の原因確認に先行させない。標準7文で主対象の基本形照会が保持されることは確認済みで、候補間最大への追加だけでは支持は下がらず、本文負担を解消しないためである。

現在の[接続条件](normalization-connection.md#接続条件の訂正)と保存結果を維持し、同じ22本文の再実行は行わない。次の実装前に、採る構成、残る仮説、必要な最小検証、結果による次の判断を定める。目的に役立つ指摘範囲と負担を確認してから、公開API・CLI・textlintと再現可能なセットアップへ進む。

入力側の[解析と正規化を同じ出力から取得する確認](parser-connection-check.md)を経てJuman++とKNPの単一経路を採用した。[既存用法群内の平均](frame-support-check.md#完了結果と次の工程)は一名詞依存を弱めるが、一語群の依存と通常使用の希釈も残る。人手9対の結果を新しい調整判断へ使う場合は診断証拠とし、独立最終評価とは呼ばない。追加分類器・補助コーパス・新モデル・語別補修は加えない。

既存textlint接続のレビューで確認した二点は修正済み。原文への位置写像が壊れた際はエラーを返し、idle終了を待つ試験には全体期限を付けた。既存の接続試験13件が成功し、fresh contextレビューでも問題はなかった。検出器の有効性の検証とは区別する。

textlint側でinline codeを除外すると、技術文の「`Pod`を削除する」から対象語が落ちる。既存AST・library・issueの限定調査により、micromark 4.0.3の公開root APIから位置付きのcode tokenを得られることを確認した。文書全体を一度解析し、textlintのCode.range/valueと一致するtokenを元位置付きのStrとして既存StringSourceへ渡す。引用・リストの継続行はCode.raw単体の解析では文脈を失うため、Document原文を使う。backtick・padding・改行の解釈を再実装しない。

この入力保持は実装済みで、range・value・UTF-16幅の不一致は処理エラーにする。既存worker、診断形式、検査対象のParagraph/Header、entity/escapeの制限は維持した。通常codeと周辺語、複数backtick・padding、引用・リスト継続、絵文字を含む接続試験16件が成功し、fresh contextレビューに必須修正は残っていない。追加parseの固定技術文1,868 UTF-16単位での中央値は18.6ms。検出器を含む速度ではない。根拠と限定観察はGit外の`markdown-input-20261022.md`、制約は[textlintの説明](textlint.md)にある。

全文確認とは独立して、採用済みの解析器・資源接続を再現する導入手順を実装する。Git外の`standard-runtime-setup-20261022.md`に固定source、二つの既存patch、配布資源とhash、実行optionを整理済みであり、この部分は指摘境界の判断に依存しない。既存の取得物・builderを再利用し、別prefixへのclean buildと導入を確認する。大容量資源は共有cacheへ置き、再取得・複製・公開しない。Pythonは既存の`pyproject.toml`と`uv.lock`による一つの環境を基本にする。検出判断や本体APIを先行実装せず、導入時のhash照合と実行時の軽い構成確認を分け、scratch絶対pathへの依存を除く。

導入確認ではcoreとvectorの固定8依存を一つの環境へ導入し、importと固定モデルのloadに成功した。nativeの新規buildはconfigureだけで約9分を要し、初期の10分予算では残るcompileを確かめられない。停止記録を保持し、同じ新規workの標準make/cmakeから残工程を続行する。旧prefixのobjectは使わず、source・patch・optionを変えない。続行は15分・増分2GiBを上限とし、完成時の来歴には初回停止と続行の両方を含める。この測定予算を利用者の一律制約にせず、導入commandの期限は指定可能にする。再開専用の大きな管理機構は加えず、既存build工程を再利用する。

現在の判断は[目的と設計の見直し](design.md)を参照する。[構成の記録](architecture.md)は、既に検証した照合機構の説明であり、製品で採用する単位が確定したという意味ではない。

必要な情報は、既存解析による語の基本形、同じ出現の格関係、原文位置である。次の評価ではJuman++の形態素情報からKNPに構造・格・語彙正規化を取得させる。既存のKWJAを使った保存結果は比較用に保持する。公開格を能動原述語へ一律に変換済みとは扱わない。正規化そのものを未解決の研究課題にせず、固定入力・取得済み資料・保存出力を維持する。警告分類、文脈モデル、頻度による抑制を、未確認の問題への対策として追加しない。

## 工程と判断の順序

1. **課題と必要機能を定義する。** 入出力、目的、対象を明確にする。名詞の新しさ・未収録と、その名詞へ述語をどう使うかを混同しない。手段や将来の拡張を要件へ昇格させない。
2. **実現方式と検証計画を決める。** 既存研究・保守中の実装・issue等から設計判断を行う。各情報・部品がどの要求を満たすか、どこまで主張できるかを確認する。情報を保持できないことが設計上分かるなら、実験や追加モデルで埋めず設計を直す。残った仮説、必要な根拠、最小実装、結果に応じた判断、終了条件を定める。
3. **残った仮説だけを最小実装で検証する。** 工程2で定めた範囲を実施し、支持・反証・未確認を区別する。既存の証拠を再利用する。問題を見つけても、その場で対策を実装せず、原因を確認して必要な設計箇所へ戻る。
4. **構成を固定して範囲を広げる。** 工程3の結果で進行可能と判断した構成を、独立した資料・入力へ広げる。拾える対象誤用、正用への警告、未評価、原文位置を確認する。資料拡大や全量処理は、この工程の目的と予算を決めてから行う。
5. **実利用と品質を確認する。** スクリプト・textlintへの接続、常駐時の遅延、長文、Unicode・Markdown位置、容量を検証する。訂正案を実装する場合は別に評価し、fresh contextで単純さ・保守性・テストの妥当性を確認する。

設計レビューは工程表への適合だけで終えず、利用者の元の要求へ遡る。実装レビューでは、その設計への適合を確認する。少数例の成功を汎用性能の証明にせず、低い単体scoreだけで方式を捨てない。「警告候補」と呼び換えることで、目的に役立つかの確認を省略しない。

対照の正誤を検出器の出力やLLMの判断で正解化しない。寺村の原注釈、教師訂正文、利用者が挙げた問題例はそれぞれの来歴を保つ。教師訂正文は完全な正用goldではない。固定groupの保留testは、この工程の調整には使わない。

## 再利用する結果と停止している作業

- **保存・検索:** 完成1,000段落の索引で、保存形式の変更後も全件数・記事数・引用・候補が一致した。固定4入力では341出現の照合・位置保存に接続不一致を認めなかった。対象用法の選び方や誤用検出性能の確認とは別である。
- **存在照合の費用:** 固定12入力で打切りなく完走。16〜71字の9入力は0.031〜0.072秒、1,900字は2.073秒、初回loadは14.396秒。1周・1,000段落索引の結果で、一般的な速度の保証ではない。別経路の名詞一般化等の54〜67秒を混ぜない。
- **未観測結果:** 固定4入力の全341出現中327出現が未観測で、そのnodeの位置は各全文を覆った。参照45記事では対象の二語関係も未収録だった。誤用率・誤警告率でも、一般分類器が必要という証拠でもない。数値と解釈の訂正は[検証記録](minimal-validation.md)にある。
- **全量解析:** 69,195文書の処理は23,670文書を保存した状態で安全に中断し、`complete=false`を維持した。原本と完成1,000件の資料は保持している。設計の見直し完了だけを理由に全量処理を再開しない。
- **未採用の追加案:** 頻度・association、旧構造索引での上位名詞拡張、参照文脈prototype、9枠、HGB、それらを必須としたruntime接続。参照encoderの全量計算は未開始。現在検証している格フレーム内の名詞支持とは区別する。研究・部品は保持するが、既に書いたことを採用理由にしない。
