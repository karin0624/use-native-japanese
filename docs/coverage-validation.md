# 既成辞書との接続を入力全体へ広げる

目的は、既存の正規化・格解析と大規模な用例集約を組み合わせたときに、対象の使い方がどのような結果になり、その理由が何かを確かめること。少数例の成功を汎用性能とみなさず、別手法の横並び試行は行わない。

## 開始条件と残る問い

[参照準備](reference-preparation.md)の実ファイル読取りが成立してから照合を実行する。入力の固定と、検証済み解析経路を再利用する準備は並行できる。辞書形式に未解決の不一致があれば、そのまま全入力を投げて未観測件数を数えない。

残る問いは、固定した構成で、対象例の語の結び付きと原文位置を保持して照合できるか、結果を見ずに選んだ文章全体ではどの程度の関係を照合できるか、未観測や未処理の具体的な原因が何かである。学習、頻度による警告抑制、名詞一般化はこの検証へ追加しない。

## 入力を先に固定する

- 既存E1とC1は保存済み解析を再利用する。教師例E1の元訂正文、既存`teacher:723`の原文と元訂正文、利用者提示の「重複を畳む」を追加する。新規解析はこの4本文だけ。教師の元span・訂正・来歴を保ち、利用者例に新しい正解spanや訂正文を付けない。
- 取得済みMIRACL日本語Wikipediaの2019-02-01 snapshot、固定5%集合から16段落を追加する。`docid`末尾が`#0`、本文100〜500文字、旧31参照と別記事という条件で、`sha256("coverage-20261022:" + docid)`の昇順から16件を選ぶ。語・述語・検索結果・正誤判断で選び直さず、段落全文と出典を保持する。100〜500文字の条件は今回の処理予算のためであり、製品の入力制限ではない。
- この16件は題材の違う入力での照合範囲と指摘負担を見る資料で、完全な正用データでも参照辞書からの独立を保証する資料でもない。サ変述語・形容詞の関係が実際に含まれるかも記録し、含まれない型を検証済みにしない。

対象誤用の選択理由は`/workspace/scratch/target-input-next-stage-20261022.md`にある。存在動詞の生物性、正用同士の意味差、自他の問題を、今回の必須検出例へ混ぜない。

## 同じ経路で全文を処理する

既存Juman++の正規形、KWJA word tinyの主辞・PAS、rhoknpの原文内の項を使う。取得条件は従来と同じ`get_all_arguments(relax=False, include_nonidentical=False, include_optional=False)`とし、この公開APIが返す原文内の項をすべて全文から列挙する。「すぐに」等の修飾的表現や共参照による追加項までを「すべて」に含める意味ではない。特定の語を探してから照合する処理は入れない。文・形態素・表層・位置の同一性を確認し、既に検証した空白の座標対応とliteralな入力接続を再利用する。欠損値や対応不能を推測で補わない。

各関係に原述語と相手語の表層・正規形・格・原文位置、辞書読取り結果と根拠を保存する。用例未観測、辞書key未収録、解析や形式の未処理を混ぜない。入力の誤りspanに交差したかという集計は元注釈との対応に限り、一般的な検出率とは呼ばない。

同じ常駐解析器を使い、新規20本文を一周だけ解析する。モデル・依存は既存の固定版を使い、新規取得は行わない。起動込み10分を上限とし、完成分を保存する。起動・文書ごとの解析・辞書照合の時間、親子processの最大観測RSS、関係数、照合状態、位置不一致を記録する。上限で未完成なら未処理のまま原因を確認し、別モデルの試行へ移らない。

## 結果から判断する

対象例では、原語と訂正語がどう観測されたかをframe・原値と対応させる。原語にも記録があれば消さず、この有限資料で指摘できない理由を説明する。一般文章の未観測は、原文・解析値・辞書keyへ戻って確認する。未観測の独立keyが20以下なら全件、それより多ければkeyのJSON表記のSHA-256順で20件を読み、都合のよい結果だけを採らない。

照合が成立しても、未観測をすべて誤用と認定しない。解析・正規形の接続不備、資料の未収録、実際の使い方の違いは、それぞれの証拠で判断する。追加機構が必要になった場合は観測した不足と関連研究へ戻り、先回りして分類器等を足さない。目的に役立つ指摘範囲と制約を確認できた段階で、製品の公開API・CLI・textlint接続と再現可能なセットアップへ進む。

## 全文検証で判明した接続上の不足

2026-10-22、新規20本文と保存済み2本文を完了した。起動込み124.993秒、親子processの最大観測RSSは1,546,203,136 bytes、原文位置不一致は0件。270関係中、支持89、未観測121、Juman++のcanon欠損による照合不能60。辞書へ渡せた193種類のkeyでは、全て対象欄の読取りが完了した。この数字は検出精度ではない。

利用者例「重複を畳む」は未観測、E1の対象は未観測、元訂正とC1の対象は支持だった。`teacher:723`の「しめる」はJuman++の第一表記が「占める」であり、「閉める」の照合成功例とは扱えない。訂正「けす」は「消す」として支持された。活用の正規化と、曖昧な語の選択は別の問題である。

一般文章の未観測109種類から、計画どおりkeyのSHA-256順で20件を原文まで確認した。次の不足は、未観測を抑える機構の必要性ではなく、比較対象を作る接続へ戻る根拠となる。

- **語彙単位の損失。** 主辞一形態素をそのまま比較したため、「一体化」が「化」、「中心的」が「的だ」、「長さ」が「さ」になった。原文全体と位置を保存できても、照合keyが元の語を保持したことにはならない。接辞ごとの結合規則をアプリ側へ足さず、既存の語彙単位正規化を調べる。
- **関係の種類の混在。** 「駅名を変更する費用」の「費用―ノ―変更」、名詞の定義文、本文で省略された項の推定などが含まれる。全基本句の`pas`というAPI名を、全てが対象の述語項関係である根拠にはできない。既存のPAS・連想照応・省略関係の定義と公開取得条件を確認する。
- **入力の格と辞書欄の対応。** 「架空の人物」は入力側で「架空だ―ガ―人物」となり、辞書のガ欄では未観測だった。辞書には別に`ノ格~ガ`等の欄があるが、同じ関係へ対応できるかは未確認。表記を独自に切り分けたり、別欄を一律に同じ格としたりせず、生成元と既存consumerの仕様へ戻る。

canon欠損には固有名だけでなく「基質」「機序」「皇籍」も含まれ、造語の問題へ一括しない。以上の不足を残したまま未観測を製品の指摘へ変換しない。既存の正規化・関係の選択・辞書との対応に必要な情報を先に定め、公式実装、研究、issue、利用例から接続方法を検討する。比較方式全体の破棄や追加モデルの採用は、この結果からは導かない。

原結果は`/workspace/scratch/coverage-probe-20261022/`の`run-02/`、`summary.json`、`unobserved-audit.json`に保存した。起動前の実行記録schema不一致で止まった`run-01`も保持しており、新規解析は`run-02`の一回だけである。
