# 今回の実装と完了確認

今回の完成条件は、誤った語の使い方を位置付きで指摘する方式を検証したツールと、所定形式の用例追加による改善・規模拡大を示すこと。全例の正答や辞書未収録の解消は求めない。追加指示と既存結果に基づき、未実行の4全文に対するDの全境界再集計を必須工程から外す。

## 固定する判断

既存Juman++・KNP・公開PASとF/C/N/Hの接続条件を維持する。同じ出現の述語、型、格、名詞で照合し、原文の名詞・述語の端点を返す。文法・活用・助詞の解釈は追加実装しない。

直接の観測があれば指摘しない。観測がなく比較可能な通常frameがある場合は、既存の名詞支持を群方向への類似度Dで計算する。比較可能なaliasを実語内で平均し、実語を等票で平均したμに対して `D = x·μ / ||μ||` とする。実語平均の途中正規化、頻度重み、上位語への切詰めは加えない。通常frame・公開候補間の最大を使う。比較不能・厳密zero・非有限値は数値0にせず、不能理由を返す。

この選択は、raw平均が群方向と集中度の積になり、通常使用の支持も下がるという観測に対応する。Dではラベル・機関車の支持が回復し、ネックレスの着る／持つの区別は悪化した。この既知の誤支持を隠さず、Dを正誤確率とは扱わない。根拠は[全文確認](full-text-support-check.md)末尾と、Git外の`prototype-support-check-20261022/report.md`にある。

既使用の診断資料から暫定境界を **D < 0.35** に固定する。主対象の保存値約0.336とラベル約0.420の間に置いた実験的な運用点であり、最適閾値や一般的な日本語の境界ではない。利用者が値を指定できるが、今回の評価では変更しない。直接観測のない低支持関係へ確認を促す指摘を返し、単なる未観測一覧を完成品とはしない。比較不能を指摘なしだけで隠さない。

## 小さい製品構成

- Python APIは同じ常駐解析器と参照を保持して`analyze`／`lint`を提供する。rhoknpの既存常駐I/Oを使い、独自のIPCやnative監視を作らない。異常終了・timeout・位置不一致はエラー、公開fallbackは該当文の解析不能とする。
- CLIは検査、既存JSONL形式の常駐worker、正規化用例の書出し、追加用例の取込、派生索引の準備を提供する。既存textlintの`command`配列とUTF-16診断形式へ接続する。Python内部の範囲は文字添字とし、外部への出力時に変換する。
- 統合レビューで、textlintがPythonの解析不能・参照不足を表示せず、指摘なしに見せる不一致を確認した。JSONLの`unavailable`に種類・理由・端点を集約し、既存の位置変換を通して「判定保留（解析情報）」「判定保留（比較不能）」を表示する。誤用指摘とは文言を分け、参照不足を誤用認定や段落全体の処理失敗へ変えない。
- 型は正規化照会、端点、関係、解析不能、検査結果の小さなdataclassで共有する。巨大な実験audit、固定例ID、scratch path、実験runnerは製品へ移さない。
- native設定の起動前確認と固定vectorの安全なloadはsetupと本体で共有する。数GBのhashを文ごとに走査しない。

## 情報追加の形式

追加は出典付きの正規化用例JSONLとする。1行は版、正規化契約、述語、述語型、格、名詞全体、出典ID、出現ID、出典の所在を持つ。正規化契約は採用した`knp-standard-cv-head-v1`と対応させる。`extract`が既存解析の同じ出現と照会候補からこの形式を書き出せるようにする。用例の正しさや出典の利用条件を解析器だけで保証するものではない。

取込器はJSONの検証とSQLiteへの保存だけを行い、日本語の再解析や成分aliasの組合せ生成をしない。直接支持の完全一致キーは `(述語, 型, 格, 名詞全体)`。別出典の同じ組も出典対応として残すが、頻度による加点はしない。繰返し取込は重複登録せず、不正な行のある取込はtransactionを取り消す。既存配布辞書を変更せず、直接支持へ追加集合の一致を加える。群の更新や、追加用例から未追加語への一般化は今回の必須範囲に含めない。

## 保存量と実行費用

追加する異なる用法をE、出典との対応をR、表記・出典等の総bytesをLとすると、固定本数のSQLite索引で追加保存は`O(L+E+R)`となる。用法の完全一致検索は概ね`O(log E)`、代表出典1件の取得まで含めると`O(log E+log R)`である。全名詞対、全入力×全参照、原文全文の重複保存は不要。原文を別途保持する場合はその容量も分けて示す。標準の[sqlite3](https://docs.python.org/3.12/library/sqlite3.html)と[複合索引](https://www.sqlite.org/queryplanner.html#_multi_column_indices)を使う。

既成CDBはread-onlyのまま使う。名詞IDの逆引きは一度SQLiteへ準備し、要求ごとの辞書全走査を避ける。群のμ・件数・不能件数を必要になった群ごとに一度保存し、支持計算では関連群に対する内積を行う。保存は語のalias対応量と`O(Gd)`、準備後の支持計算部分は`O(G_q d)`。d=300、Gは保存群数、G_qは同じ述語・型・格の群数。これとは別に、現在の基底照合は同じ述語のrecordを読み、実語ID列を走査して直接観測を調べるため、その参照量に比例する費用がある。照会全体が内積だけになるとはしない。入力名詞ごとの参照一覧やcosine行列は保存せず、資源・モデル・方式が異なるcacheを混用しない。

既存CDBの複合aliasには組合せ積があり、**構築時間の制約は残る**。組合せを逐次集約して平均のみ保存し、全組合せの永続化・同時保持はしない。追加するflat用例はこの展開へ入らない。恣意的な件数打切りや語別の除外で、未計算を計算済みにしない。初回の索引準備・未準備群の計算と、常駐時の検査遅延を分けて測る。

## 検証と終わり

1. 実装後、fresh contextで数式・原語接続・位置・データ追加・保存量・不要なテストを確認する。既存の少数診断入力を現在の解析器で通し、主対象の原語と格を保持して位置付き指摘へ届くこと、直接観測の対照を指摘しないこと、既知の不能や誤支持を保持することを確認する。全例分離は条件にしない。
2. 評価前に入力と追加出典を固定する。既存の未使用資料への一度の適用で、指摘・不能・端点を報告する。原注釈へのoverlapと今回の語の使い方への到達は分け、未注釈全文を完全な正用goldとは呼ばない。結果を見て同じ評価入力へ境界を合わせない。
   実適用で、技術文中の`>`を含むKNPの公開素性をrhoknpが読めない事例を確認した。上流形式に起因する処理失敗は原文・出力・原因を保存して分母に残し、他の固定入力を続行する。同じ失敗を再試行したり原文を書き換えたりせず、追加前後の比較不能も明示する。索引や計算、位置対応に新たな実装不備があれば、その原因確認を優先する。全ケース対応を今回の追加条件にしない。
3. 同じコード・境界・評価入力で、別出典に自然に現れる用法を追加する前後を比較する。通常使用への不要指摘の減少、対象誤用への指摘維持、悪化・無変化・不能を全て示す。入力文そのものの登録や、手作業で作った正解用例を改善証拠にしない。必要な用例が無いことだけで方式全体を棄却しない。
4. 内容の異なる実用例を段階的に増やし、観測数・種類数・入力bytes、DBと一時fileの容量、取込時間・RSS・同じ照会の遅延を測る。同一情報の再取込で増えないことも確認する。構造上の増え方と実測を併記し、少量の実測だけで大規模性能を保証しない。
5. Python→JSONL→textlintを通し、Unicode・Markdownの位置と常駐動作を確認する。短い段落（200文字以内）の再検査について1秒以内を今回の測定目標とし、初期化・初回の群準備・再検査を分ける。未達なら原因に対応する最小修正を検討し、別方式の総当たりへ戻らない。

以上から、目的に役立つ指摘と情報追加による改善、拡大時の費用を説明できれば今回を完了する。全日本語での正答、全用例の取得、新モデルの比較、訂正候補は追加の終了条件にしない。
