# 最小の用法照合

目的は、AIが出した誤った日本語をリアルタイムで位置付き指摘し、可能なら訂正案を出すこと。まずは**既存の構文解析から比較条件を列挙し、用例に一致しない箇所を原文位置付きの警告候補として示す**構成を検討する。

## 最小経路

1. 参照資料を既存解析器で解析し、観測された語と構造の組み合わせを索引へ保存する。
2. 入力も同じ解析器・同じ比較条件で解析し、全候補を照合する。
3. 各候補について、索引内で観測済みか未観測かを返す。
4. 未観測の組み合わせを原文位置へ対応付け、警告候補として示す。

照合前に疑わしい箇所を選ぶモデルは置かない。全照合の費用が実利用で問題になった場合に、必要な速度対策を考える。索引の未完成・版違い・解析失敗は処理の失敗であり、用例の未観測とは区別する。

「用例がない」を「使われにくい」へ細分化する採点、頻度・記事数による閾値、名詞類似度による保留、入力BERT、参照文脈prototype、固定9枠、HGB分類器は、この最小経路に含めない。既存の調査・実装は追加候補として保持するが、現在の必須部品とは扱わない。

## 比較条件と原文位置

原文の全文・文字位置と、既存解析器のtoken、lemma、UPOS、head、dep、文境界を保持する。解析器・辞書・schemaの版を固定する。日本語の複合述語・格・活用を独自の規則で修復しない。

実装済みの照合基盤は、GiNZAの公開依存木にある2〜4 nodeの弱連結な誘導部分構造を扱う。原文順の各nodeのlemma・UPOSと、有向depを一つのkeyにする。分岐を含む構文的n-gramの原理は[Goldberg・Orwant 2013](https://aclanthology.org/S13-1035/)を参照し、集合列挙は既存のigraphへ委ねる。

「精度を高くする／大きくする」のように、独立した二語の関係では消える共同条件を保持する。4 nodeは現在の検証上限であり、全用法を表せる保証ではない。全候補を照合することと、任意の日本語誤りを検出できることは異なる。原文の離れた関係nodeの間を、全て誤語と決め付けない。

## 存在照合と保存量

同じ組み合わせを集約し、頻度1の観測も削除しない。原文の検索を毎回行わず、完成索引のkeyを照合する。原文・位置へ戻る引用は、必要な根拠を確認するために保持する。

現在の実装はSQLiteで構築し、marisa-trieとArrow IPCの圧縮配列から読み出す。共同件数・周辺分布・名詞候補の索引も既にあるが、**存在照合だけの経路では、それらの値を取得・採点する必要はない**。全派生条件の事前集計も最小の情報要件ではなく、保存形式はこの区別に沿って整理する。

既存の固定1,000段落では、件数等を含む索引を全値一致のまま174.7MBから60.0MBへ縮小した。これは最小の存在索引の容量でも、全参照資料の実測でもない。1%の参照集合は検証範囲であり、製品の対象範囲へ読み替えない。

## 次に確認すること

- **一致判定と位置:** 同じ比較条件で実在用例が一致し、未観測のkeyが区別され、原文位置が保たれること。
- **全候補照合の費用:** 解析・列挙・存在照合を分けて測る。名詞候補の全走査や周辺統計の取得時間を、存在照合の費用へ混ぜない。
- **警告候補の実際:** 既存資料で拾える誤用と不要な警告を読み、どこに不足があるかを確認する。未観測は選んだ資料内の事実として表示する。語彙誤用・正用への警告・資料不足の観察を、少数例の成功で置き換えない。

追加機構は、この経路で判明した具体的な不足を解消する場合にだけ選ぶ。多義性が一般に存在することや、誤警告の可能性があることだけで、文脈モデルや分類器を先に必須化しない。訂正案は検出とは別の任意機能であり、用例のlemmaを活用済みの修正文としてそのまま提示しない。
