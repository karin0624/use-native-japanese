# 現在の解析・照合構成

AIが出した日本語から、用例に裏付けられない語の使い方を位置付きで指摘する。目的、対象、支持の仮説と完成条件は[設計](design.md)を参照する。以下はIssue #15で採用するv10の構成である。新規用例なしで同じ6,463本文の最終再構築・限定評価を完了した。条件と結果は[v10の検証](projection-validation.md)に記す。

## 原文から位置付き指摘まで

1. GiNZAの既存C分割を済ませ、既存のASCII識別子範囲を公開retokenizerで一tokenへ結合する。
2. 結合済みの同じDocを`ja_ginza`の特徴生成・依存解析・品詞解析・文節処理へ渡す。NERは使わない。
3. 文節間の元`nsubj`・`obj`・`iobj`・`obl`・`acl`・`amod`を読み、元anchor・UPOS・向きを保持する。
4. 両anchorの所属文節から機能表現と非語彙を除いたlemma列を作り、同じ契約の参照へ照会する。
5. Bloom陽性または名詞一般化で支持があれば無指摘、なければ両端へ通常`error`を返す。処理異常は`systemerror`とする。

解析契約は`ginza-bunsetu-functional-projection-v10`。公式GiNZA 5.3.0、ja_ginza 5.3.0、spaCy 3.8.16、SudachiPy 0.6.11、SudachiDict-core 20260723を固定する。GiNZAと必須依存、軽量モデルを維持し、別の解析器を重ねない。

ASCIIの境界は[UAX #29の連続英数字word](https://www.unicode.org/reports/tr29/tr29-49.html#Word_Boundary_Rules)と、従来の英字/_開始の記号を含む識別子profileを分ける。全体のpatternは`(?<![A-Za-z0-9_.-])(?:[A-Za-z_][A-Za-z0-9_]*(?:[.-][A-Za-z0-9_]+)*|[0-9][A-Za-z0-9_]*)`。数字開始の記号結合は増やさず、日付・算術を新たな一語へまとめない。`Doc.char_span(..., alignment_mode="strict")`で元token境界に合い、複数tokenに分かれた範囲だけを結合し、そのlemmaを原文表記とする。一tokenの公開lemmaは上書きしない。解析後の投影や語別一覧は使わず、C分割の補助データは結合前に既存処理で消費する。同じ本文には.md/.txtで同じ処理を適用する。

比較語彙は`ginza.bunsetu_span`による元anchorの所属文節から取得する。位置分類`FUNC`・`SYN_HEAD`または公開依存関係`aux`・`case`・`cop`のTokenと、それらをheadとする文節内の`fixed`直接子を除く。`CONT`は位置分類なのでcase/auxも中に現れ、語彙の保証にはならない。`mark`・`cc`等を依存ラベルだけで追加除外しない。公開`is_punct`・`is_space`以外を非語彙と決めず、`NO_HEAD`を含む残りの公開lemmaと原文との対応を全て保つ。元anchorが除外された関係を同文節の別語に付け替えない。表示は保持したTokenの先頭から末尾までの包絡一範囲とし、比較には各Tokenのlemmaだけを使う。包絡の途中にある非選択語は比較lemmaへ加えない。同文節の修飾も条件に残り、完全な語彙IDや厳密な複合語境界ではない。

機能表現は公開`Token.children`から、上記の機能側Tokenをheadとする文節内の`fixed`直接子を読むだけで取得できる。当方forkの追加句APIを使う必要がなくなったため、公式GiNZA 5.3.0へ戻し、vendor wheel・patchを撤去した。必要な語彙・関係・位置を既存の公開出力だけで得られることが理由であり、ライブラリ数の数合わせではない。主辞句の選択集合を語彙全体とする旧方式は使わず、元の文法・lemma・依存辺・文節境界を独自に修復しない。

前四種の依存関係では従属側をN、元headをPとし、`acl`・`amod`ではheadをN、従属側をPとする。役割は元UPOSから独立して保持し、NOUNをVERBへ変えない。`advcl`・`nmod`・`compound`等から品詞だけで独立の用法を作らず、各節の明示された対象辺を読む。名詞側が既存辞書の詳細品詞「助動詞語幹」に属する機能カテゴリは従来どおり対象外とする。元解析の誤辺や未取得の関係は修復しない。

照会キーはPのlemma列・元UPOS、元依存ラベル、Nのlemma列・元UPOS、Nの元方向（head/dependent）。Bloom陽性の`indexed`には低確率の誤通過がある。陰性ならN以外の条件を固定した用例群と比較し、異なる名詞列を等票にした300次元ベクトル群平均の方向へのcosineが0.35以上なら`supported`とする。原Pは一般化しない。平均・閾値は再検証する仮説であり、正誤確率ではない。

いずれの支持もなければ両端を通常`error`とする。ベクトル不能・群なしは追加支持なしとし、数値0を作らない。解析失敗・資源破損・非有限値・契約不一致は`systemerror`。Python位置は文字添字、CLI・JSONLはUTF-16へ変換し、textlintが原文へ戻す。訂正案は未実装。

## 用例の構築と配布を分ける

用例本文を入力と同じ契約で`extract`し、出典付きJSONLを`import`して構築用正本SQLiteへ保存する。`prepare`で重複排除した直接集合のBloomと、名詞群平均・件数・契約情報を配布参照SQLiteへcompileする。追加後は全量を再compileし、新しい参照で検査器を起動する。

構築用正本は組合せと出典・出現の対応を保持し、原文全文は保存しない。検査端末には正本・全出典・全用例の個別ベクトルを要求しない。固定モデルと配布参照はGit LFSで管理し、npmへ実体を同梱する。原コーパス本文と正本は公開しない。

異なる組合せ数N、群数G、次元d=300、配布文字列量L、Bloom誤認率pに対する保存量は`O(N log(1/p) + Gd + L)`。p固定ではこれらの件数等に比例し、全名詞対や入力×用例の行列は作らない。同じ組合せの出典だけが増えても配布集合・群平均は増えず、正本の出典対応は別途増える。固定Bloomの容量を超える前に正本から再構築する。

Bloom単体の圧縮率を配布全体の容量とみなさない。平均はf64で2,400 bytes/比較可能群にキー・件数・SQLite管理領域が加わる。v10の新参照は89,964,544 bytes、固定モデルは21,944,687 bytes。既存8本文の追加は136用法・22群、配布参照106,496 bytesの増分だった。[v10の構築費用](projection-validation.md#データ量と構築費用)には、保存Doc再利用と差分405本文の実推論を用いた測定条件を記す。二点の小差分で本文量に対する線形性は証明しない。

## 検証記録の扱い

[v10の限定評価](projection-validation.md)と[旧三結果契約の検証](three-result-validation.md)、[旧KNP方式の結果](runtime-validation.md)を区別する。語彙取得件数や無指摘件数の変化を精度改善とみなさず、旧スコア・遅延をv10へ流用しない。Python135＋19 subtests、Node24とRuffは通過し、fresh contextレビューは指摘0件。最終資源でのcheckout・別リポジトリへの配布物導入・実textlint4呼出しも成功した。初回起動3,500.91msと同一workerの後続13〜18msは並行処理のある環境での一回測定であり、速度保証ではない。対応3OSの導入・実行は[PRのCI](../.github/workflows/npm-package.yml)で検査し、その実行結果を参照する。
