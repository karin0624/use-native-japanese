# 述語と組み合わせの用法照合

## 目的と対象外

この文書は、[製品の目的](../../README.md)を実現する解析機のうち、開発途中の第1の解析機`PredicateJudge`を説明します。本文中の述語構成や名詞との組み合わせを用例へ照合し、支持のない使い方を位置付きで指摘します。Python API・CLI・textlintから利用できます。

リアルタイムの指摘と商用利用を想定します。用例の追加・規模拡大に伴う精度、容量、構築・検索費用も検証対象です。開発計画と受入条件は[ロードマップ #38](https://github.com/karin0624/use-native-japanese/issues/38)で管理します。

現在の解析機は、名詞自体の一般性、文の重複・冗長さ、不要な否定表現を専用に判定しません。正用同士の意味差、AI生成かどうかの判定、分野ごとの文体も扱いません。製品の目的に含まれる修正案の生成は未実装です。

## 入出力

入力は日本語本文、出力は照合結果と、支持がない述語・関係の原文範囲とメッセージです。述語単独の照会ではその述語の位置、関係の照会では両側の位置を指摘します。現在の出力に修正案は含まれません。

| 結果 | 出力 |
| --- | --- |
| 用例による支持あり | 指摘なし |
| 支持なし | 書き手への通常のerror |
| 解析・資源・通信などの処理異常 | systemerror |

支持なしは参照資料での判定であり、日本語全体での不存在を証明しません。

## 共通の解析契約

原文全体とKWJAが返す全解析情報を`Analysis`に保持します。各判定機へ同じ`Analysis`を渡し、各判定機はその全情報から必要な情報を参照します。局所的な比較範囲は元データへのviewとして別に示します。

原文、全KNP出力のUTF-8 snapshot、全形態素の原文位置を不変値で保持します。KNPには形態素・基本句・文節・係り受け・述語項構造・照応・素性を保存します。`restore_doc()`は公開APIの`rhoknp.Document.from_knp()`で独立した文書を復元します。原文はKWJAの正規化後の文字列と分けて保持し、空白・CRLF・表記を原文どおり復元できます。保存形式は[API仕様](../reference/runtime.md#用例jsonl)で定義します。

## 現在の照合条件

以下は`PredicateJudge`の現在の方式です。製品全体や追加する解析機に、同じ照合方式を要求するものではありません。

- 元解析の基本句・用言認定・述語項構造を直接使います。
- 述語は構成を含めて用例にあることを必須とします。「畳む」と「畳ませる」は異なる構成として照合します。
- N–P関係は厳密なPと名詞表現の語彙的な組み合わせとして照合します。類似度は同じPの実共起群内のN比較だけに使います。助詞を含む文型の適否は判定しません。
- P–P関係は、双方の全構成と元関係が一致する実共起群の存在によって判定します。
- 照合規則は入力と用例へ共通に適用します。

構文上の条件から用例を共有できる場合に、動詞の原形などを比較して異なる構成の用例から判定する機能は未実装です。成立条件と根拠を調べ、元の構成・役割を保持して適用できるかを[構文条件による用例共用 #30](https://github.com/karin0624/use-native-japanese/issues/30)で検討します。

## 解析と比較範囲

[Parser](../../src/native_japanese/parser.py)は、公式の`rhoknp.KWJA`からKWJAのbaseモデルを呼び出します。`char`・`word`の各moduleで、文・形態素の分割、品詞・活用、基本句・係り受け・述語項構造などを解析します。基本形・代表表記にはword moduleが辞書から付与する値を使います。位置対応にはKWJAのNFKC正規化と公開文字変換表を用い、元形態素を原文範囲へ対応付けます。正規化で文字数が変わる表記も、対応する原文の範囲を保持します。解析形態素と対応付けできない場合は処理異常にします。

`PredicateJudge`は`Analysis`を受け取り、[UsageStructure](../../src/native_japanese/comparison.py)で元形態素の`global_index`を参照する局所viewを作ります。比較範囲の同定・照会・対応検証はこの判定機の内部で行います。

### 述語構成P

KWJAの基本句素性に`用言`がある基本句を述語として認識します。認定の証拠は元基本句の素性・主辞・元依存関係・品詞へ対応付けます。その基本句のうち、主辞以外の特殊品詞を除く全形態素をPとし、元の主辞を根として保持します。助詞と基本句内の接尾辞もPに保持します。

同一の元文節内で、主辞の品詞が`接頭辞`であり、元の基本句依存がPへ接続する基本句は、再帰的にPへ含めます。「再／利用」のような語形成では、接頭辞基本句と用言基本句を一つの構成として照会します。別文節の接頭辞、同文節の非接頭辞名詞、基本句をまたぐ接尾辞はこの規則に含めません。補助的な構成が基本句をまたぐ場合は、個々のPと元のP–P関係を照会します。

P・Nの語彙キーは、元形態素の代表表記`canon`を優先し、欠ける場合は`lemma/reading`を使います。表記と読みの全体を厳密照合に保持します。元の基本形・読み・代表表記候補はKNPに保存します。

Pの厳密キーには、根の相対位置、形態素の相対語順、各形態素の語彙キー・品詞・細分類・活用型・活用形と、構成内の元基本句依存を含めます。活用情報が異なる構成は別のキーになります。構成内の辺は元基本句の主辞間の依存を保持し、形態素内部の依存辺は推測しません。吸収した基本句依存は`Comparison.targets`の`scope="composition"`として保持し、外部N–P関係として重複照会しません。

### 評価関係とN

Nは、項・修飾対象として働く名詞表現の比較範囲です。両端が述語として働く関係はP–Pとして照会します。元基本句の`体言`・`準体言`素性を使い、名詞化された述語の外側はNとして扱います。

| 元解析 | 保持する元情報 |
| --- | --- |
| 述語項構造の文書内参照 | 元の格を`PAS:ガ`・`PAS:ヲ`などの形で保持し、C・N・Oなど元の項の種類も保存 |
| 述語と、述語または体言・準体言基本句の依存関係 | 元の依存種別を`基本句:D`などの形で保持し、従属側を`dependent`として保存 |
| 述語から体言・準体言基本句への修飾 | 元の依存種別を保持し、修飾先を`head`として保存 |

N–Pの照会は、元の格・項の種類・方向・接続点と分けて作ります。照会の役割は`N-P`、名詞側は`noun`、Pの接続点はP内の根へ統一し、同じ厳密PとNの語彙的な組み合わせを確認します。「父に似る」と「父から似る」は、同じ「父」と「似る」の構成を参照します。この支持は、助詞を含む表現全体の適否を認定するものではありません。元の情報は`RelationTarget`・`OccurrenceView`・KNPに保持します。

述語項構造の取得には公開APIの`pas.get_all_arguments(relax=False, include_optional=True)`を使います。同じ基本句ペアに述語項構造がある場合、その基本句依存を重複して照会しません。文をまたぐ文書内参照も元の参照先を保持します。外界参照は原文位置を持たないため位置付き照会の対象にせず、全情報をKNPに保存します。

Nの元基本句subtree全体と基本句間の依存辺をviewに保持します。語彙特徴の範囲は別に定めます。N内部の助詞と特殊品詞を除きます。ただし、元基本句が`用言`・`体言`・`準体言`と認定した主辞は品詞にかかわらず保持します。主辞自身を格標識として除かず、主辞以外の助詞と分けて参照します。評価中のPがNの元subtreeに含まれる関係では、そのPを根とするsubtreeを語彙特徴から除きます。残る全形態素の語彙キーを`Vectors.compose`へ渡します。fastTextの取得時だけ末尾の`/読み`を分け、表記部分を使います。表記中の`/`は保持します。内部にある述語もこの範囲にあれば含めます。

関係の両端は各側の元形態素を原文へ対応付けた文字範囲です。連続しない範囲は別々に示し、表示文字列は先頭から末尾までの原文です。

## 支持判定

解析契約の識別子と固定版は[models.py](../../src/native_japanese/models.py)、交換形式は[API仕様](../reference/runtime.md)で定義します。照合は入力と参照に同じviewを適用します。

1. Pを厳密な述語索引へ確認します。P単独の照会はそのPの存在だけを判断します。
2. P–P関係は、両Pの全構成・活用・根、双方の接続点、元の格または依存種別と方向が完全一致する実共起群をSQLで照会します。群が存在するときだけ`indexed`とします。
3. N–P関係は、同じ厳密Pの実共起群を確認します。異なるPのNを流用しません。群がなければ`review`とします。
4. N–Pの群があれば、Nの語彙キー列も含むキーがBloom陽性なら`indexed`にします。陰性なら、群内の異なるN特徴列を等票で平均したベクトルと入力Nを比較し、cosineが境界以上なら`supported`にします。
5. 支持がなければ`review`として原文位置を指摘します。

認識した各P・各関係から照会への対応、接続点・役割・N特徴を検査前に検証します。対応の欠落や空照会は処理異常です。各関係を個別に判定し、その結果を全て集約します。N内の述語も独立したPとして照会します。空文・空白・通常の名詞句など、正当に対象がない入力は無指摘です。

既定境界は0.35です。これは名詞側の近似比較だけに使います。平均はNの語彙特徴を語順によらず近似する値です。Nの近似比較は、同じ厳密Pの群内に限ります。ベクトルを取得できない場合は、類似度を未算出として追加支持なしとします。資源破損・非有限値・解析契約の不一致は処理異常です。

## 根拠と制約

解析は[KWJA](https://github.com/ku-nlp/kwja)、原解析の保存・復元と述語項構造の参照は[rhoknpの公開API](https://rhoknp.readthedocs.io/)を使います。P・Nの範囲は、この固定解析版の用例照会規約です。支持推定の研究上の位置付けは[先行研究](../research/prior-research.md)を参照してください。

元解析の分割・基本形・係り先・用言認定・述語項構造の誤りは後段へ影響します。構成と活用が厳密一致しない正用は参照を共有できず、異構成を静的に推論する機能は未実装です。一般の名詞同士の修飾関係は評価対象外です。

N–PのBloom陽性には、厳密に存在する群の内側で低確率の誤通過があります。群平均とのcosineと境界は名詞側の近似比較に使う指標で、正誤の確率を表す値ではありません。用例追加で判定が悪化する場合もあります。表記差とベクトルの取得範囲により正用を支持できない例があります。
