# 仕様からテストを作る

## 前提

テストを設計・追加・変更する実装者と、その妥当性を確認するレビュアーを対象とする。テストは、実装から独立した受入仕様と期待の根拠を定めてから作る。

- **ユーザー要件**：利用者が達成したい目的と、有効な制約。
- **受入仕様**：その要件を満たしたと判断できる、観測可能な振る舞いと条件。
- **実装設計・仮説**：仕様を実現する方式、内部表現、原因や効果の予測。

既存コード・テスト・設計文書も検証対象であり、存在や現状との一致だけでは正しさの根拠にならない。仕様自体にも欠落や誤りがあり得るため、ユーザー要件との対応を確認する。

## 手順

### 1. 目的と制約から受入仕様を定める

原依頼と有効な訂正を読み、対象・目的・制約・対象外を確認する。実装方式を先に固定せず、どの入力と条件で、利用者から何が観測できれば受け入れられるかを書く。

内部のキー、ラベル一覧、処理手順を、そのまま利用者が求める正解へ昇格させない。必要な内部契約のテストは別に設計できるが、語法の正しさを確かめるテストの代用にはしない。

### 2. 仕様から入力群を選ぶ

受入条件ごとに、正常例、異常例、結果の違いを確かめる対照例と、必要な境界を選ぶ。同値分割は「仕様上、同じ扱いになる入力群」に適用し、実装が同じ分岐を通ることだけで同値としない。

境界値分析などの技法は、条件の境目を調べる意味がある場合に使う。日本語の判断へ無関係な数値境界を設けたり、毎回すべての技法を使ったりする必要はない。

単語や例文の暗記を受入条件にせず、何を同じ対象として扱い、どの条件の違いで結果が変わるかを確かめる。たとえば名詞と述語を対象とする仕様なら、助詞の違いでその二語が別語になると仮定せず、対象の同一性と接続の適否を分けて期待を導く。

### 3. 期待と、その独立した根拠を定める

要求、公開された契約、信頼できる言語資料などから期待を導き、根拠の該当箇所と適用条件を確認する。実装の現在出力を正解データへ無審査でコピーせず、過去版や他の実装との一致も、それ自体を正解の保証にしない。

各テストについて、次の情報を既存のIssueやテストコメントへ必要十分に残す。Issueへの共有は[開発の進め方](../../.agents/skills/development-workflow/SKILL.md#共有する時点と内容)に従って集約し、テストごとの投稿を求めない。専用台帳や新しいテスト基盤は作らない。

入力・根拠・結果の公開には[公開規則](../../AGENTS.md#公開する情報)を適用する。私的な指示・会話に由来する入力は公開せず、公開可能な代替例で確認し、その結果が示す範囲と未確認事項を分ける。

| 項目 | 残す内容 |
| --- | --- |
| 対象受入条件 | 何を満たすことを確かめるか |
| 入力・前提 | 入力、適用条件、判断に関係する版や設定 |
| 期待 | 観測すべき結果と、必要なら許容範囲 |
| 期待の根拠 | 要求・契約・資料の箇所と、その期待を導ける理由 |

構文解析値の正確な転記と、語法の適否の判断は別である。GiNZAの出力を自分の語感だけで誤りとせず、規約上妥当な分割と、後段での接続情報の欠落を区別する。未確定な構文の正解を実装から作らず、資料で決まらない点は未確定として扱う。

対象言語・課題・評価単位が違う研究成績を転用しない。

### 4. 実測する前に期待の根拠をレビューする

- 期待はユーザー要件と対応し、引用した資料をその条件へ適用できるか。
- 仕様や期待に、既存実装の誤りや未確認の設計仮説が紛れ込んでいないか。
- **受入条件に違反する実装でも、このテストに通れてしまわないか。** 対照例や観測項目が不足していないか。
- 評価の入力・条件を保ち、情報追加の評価では境界も固定しているか。評価文の参照登録を改善に数えていないか。

根拠が不足していれば、期待を確定する前に要求や資料を調べる。

### 5. 実装の観測結果と比較する

レビューした期待に基づいてテストを作り、[開発手順](development.md)から変更に必要な検査を選んで実行する。観測した出力・条件を期待とは分けて記録し、一致・不一致・未確定を受入条件ごとに判定する。

振る舞いの回帰を既存の試験へ加える。実装の写し、些細な記述の固定、個別文書だけの専用CIを増やさない。

テスト数やCI成功は、用意した検査を通った証拠である。直列化の一致やCLIとの一致も、その契約や経路の一致を示す範囲に限られ、語法の妥当性や利用者の目的の達成を単独では証明しない。

必要な確認が通ったら、条件が変わらず新たな懸念もない検査を反復しない。

## 結果

受入条件から入力と期待をたどれ、その期待を実装に依存しない根拠で説明できる。検証結果には、確かめた範囲と未確認の条件が明確に残る。

## 問題への対処

期待と実測が違う場合は、期待を実装へ合わせず、要求・資料の適用・入力条件・実装を調べて不一致の原因を特定する。誤った既存挙動の保持を回帰防止と呼ばず、根拠に従って仕様・期待・実装のどこを直すか判断する。

仕様どおりでも目的を満たさない場合は、ユーザー要件へ戻って受入仕様の不足を見直す。判断が未確定なら、正解を捏造せず、足りない根拠と確定に必要な確認を記録する。
