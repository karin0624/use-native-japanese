# ローカル検査の容量を減らす

2026-10-23（日本時間）。[課題2](https://github.com/karin0624/use-native-japanese/issues/2)の実装前の判断と検証範囲を記録する。

## 目的と今回の許容範囲

語の使い方を位置付きで指摘し、所定形式の情報追加によって改善できる目的を保つ。利用者は、近似集合索引が未登録の組合せを低い確率で登録済みと誤認することを許容した。これは見逃し側の誤差であり、実用例を直接確認したという表示にはしない。未観測を誤用と断定せず、既存の一般化と比較不能の区別を保つ。

用例の保存形式だけでなく、KNP自身が必要とする大容量辞書も見直すことが今回の依頼に含まれる。KNP固有の表記、完全な意味格、旧格フレームとの互換を目的より強い条件にしない。一方、別解析の関係を同一視したり、手書きの構文・活用・助詞規則で埋めたりしない。

## 比較から絞った構成

| 部分 | 候補 | 判断 |
| --- | --- | --- |
| 用法の集合 | 正確な圧縮辞書（MARISA） | 判定誤差を増やさない。文字列共有に依存し、容量を一律に予測できない |
| 用法の集合 | Bloom | 逐次追加できるが、同じ誤認率では静的Fuse16より容量・照会回数が多い |
| 用法の集合 | Binary Fuse16 | 誤通過の許容に対応し、静的な配布物に適する。第一候補。更新は正本から再構築する |
| 用例の一般化 | 事前計算した群統計 | 実行時の全用例・逆引き辞書を不要にする。直接の観測有無とは別に保持する |
| 解析 | GiNZA軽量モデルと公式文節API | 同じ解析で参照を生成すれば、巨大な意味格辞書との接続が不要。第一検証候補 |
| 解析 | KWJA word tiny | 既存実行で原語欠落・省略項誤結合を観測。約44MBのモデルだけでなく依存とRSSも大きく、同じモデルの再試行を先行しない |
| 解析 | KNPの係り受けモード | 格辞書は不要だが、表層関係は旧意味格と互換ではない。主候補が成立しない原因に対応するときだけ再検討する |

集合索引の根拠は[Binary Fuse論文](https://arxiv.org/abs/2201.01174)、[保守中のPython実装](https://github.com/FastFilter/pyfusefilter)、[C側の小集合構築の修正](https://github.com/FastFilter/xor_singleheader/issues/77)、[MARISA](https://github.com/pytries/marisa-trie)、[Bloom実装](https://github.com/barrust/pyprobables)。`pyxorfilter`はアーカイブ済みなので採用候補にしない。Fuse16の約18bit/件、誤認率1/65,536は一照会の目安で、語彙・出典・群統計・構築時メモリを含まない。候補を複数照会する場合の誤通過を別に数える。

解析側は[GiNZAの公式文節API](https://github.com/megagonlabs/ginza/blob/v5.3.0/docs/bunsetu_api.md)、[GiNZAの研究](https://www.jstage.jst.go.jp/article/jnlp/27/3/27_695/_article/-char/ja/)、[既存の解析調査](parser-investigation.md)と保存済み出力を根拠にする。GiNZA 5.3.0と互換性のあるSudachi辞書を固定し、最新辞書を無条件に組み合わせない。旧GiNZA試作の全2〜4頂点の列挙と、全未観測の警告には戻らない。

## 検証する仮説と順序

1. **集合索引の部品が現在の環境で安全に使える。** GPT-6.1 sol担当がGit外で`pyfusefilter==1.3.0`のPython 3.12での構築、空・小集合、別プロセスでの保存復元、登録集合の保持を確認する。人工キーは容量・所属判定だけの測定に使い、日本語の精度評価に数えない。公開形式の長さ・版・整合性を検査できない場合は、採用前に保存境界を見直す。
2. **公式文節APIだけで対象の語と関係を保持できる。** 保存済みの診断と全文へ一度適用し、元の名詞・動詞・形容詞、関係の原方向、正規化、端点を確認する。公式の文節間の依存辺を単位とし、一般化は名詞と動詞・形容詞の関係で名詞側だけに行う案を確認する。名詞述語や別文節の複合表現の不足を隠さず、独自の結合規則は足さない。旧意味格への対応表は作らない。
3. **同じ解析契約の参照と圧縮成果物で、用例に基づく検査を実行できる。** 構築・監査用の正本と、配布する集合索引・群統計を分ける。固定した自然出典から参照を生成し、同じ記録を使う正確な照会との比較で、圧縮に起因する違いと解析・用例の不足を分ける。モデルや閾値を結果に合わせて再選択しない。
4. **全体で容量と反復速度が改善する。** モデル・辞書・Python依存・参照成果物を含む実容量、構築時RSSと一時容量、起動と再検査を分けて測る。元の12文字・25文字の遅延例、技術文の形式失敗例も分母に残す。別出典追加前後の改善・悪化・無変化を記録する。

実装前の部品確認はscratchで行い、採用判断後に製品へ統合する。調査・確認済みの候補を順番に試すのではなく、上の仮説が崩れた原因に対応する工程だけへ戻る。入力と参照の具体的な選択は、採点前に保存済み資料の識別情報とともに固定する。

## 実装と終了条件

新しい解析・保存契約は明示し、旧契約と混ぜない。単一の実行経路を優先し、未採用の解析器や保存方式を製品の選択肢として増やさない。数式・公開API・通信・位置の保証に必要なテストを残し、旧実装の細部を固定するだけの試験は持ち越さない。実装はGPT-6.1 sol、採用後の単純さ・保守性・試験はfresh contextでレビューする。

容量削減と目的への適合を実測で示せた構成を採用する。全用例収録、全例の正答、訂正案は追加の完了条件にしない。元資料・モデル・生成索引はGit外に保持し、コードと日本語の判断記録だけをコミットする。
