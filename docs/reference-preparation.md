# 参照資料を広げるための準備

目的は、未知の文章を照合できる参照資料を、現実的な時間と容量で用意すること。二入力の接続確認を汎用性能の根拠にせず、取得済み全文の全量解析も先行させない。

## 今決めること

既存の大規模な解析済み用例を再利用する経路と、取得済み本文から必要な索引を構築する経路を検討する。前者は利用できる形式・条件と原語／格／出典の保持を確認する。後者は、文書ごとの呼出しで測った129.64秒を一括処理の費用へ外挿せず、公式の一括入力経路の費用を一度測る。両者の情報から、未知入力へ広げる参照範囲と処理予算を決める。

現時点では[京都大学格フレーム](https://nlp.ist.i.kyoto-u.ac.jp/index.php?京都大学格フレーム)の大規模集約と、[NLT/TWC](https://tsukubawebcorpus.jp/)の大規模用例検索が存在する。一方、GSKの申請制資料、Web検索画面、実際に自動利用できる配布物を同一視しない。既存の研究記録を再利用し、KNP配布辞書との関係など取得経路を変える不足だけを追加調査する。

## 公式一括入力の限定計測

仮説は、同じwordモデルに複数文書を一括で渡すことで、文書ごとの準備処理を繰り返す費用を減らせることである。用例の判定方法や日本語解析の独自実装を増やす実験ではない。

[KWJA 2.5.1のREADME](https://github.com/ku-nlp/kwja/blob/v2.5.1/README.md)、[CLIと公開テスト](https://github.com/ku-nlp/kwja/blob/v2.5.1/tests/cli/test_cli.py)には複数ファイル入力とbatch指定がある。実装は複数DocumentをJuman形式の中間ファイルへまとめ、同じword処理へ渡す。[上流PR 260](https://github.com/ku-nlp/kwja/pull/260)にはword推論の大きな中間配列についての報告があるが、修正先はdevであり、今回のstableへ取り込まれたとは扱わない。公開機能の存在は、CPUでの高速化や結果同一の保証ではない。

- 固定33文書の保存済みJuman++出力を使う。本文欠落を直した一件は追加出力を指定する。Juman++は再実行しない。文書境界を保ち、複数文書を一文書へ連結しない。保存値にはS-IDがなく、元IDの `#` はrhoknpのS-ID形式で受け付けられないため、公式 `add_doc_ids` / `add_sent_ids` で一意な転送IDを付け、元IDとの一対一対応を保存する。本文の文字置換は行わず、出力IDの重複・欠落・未対応を検査する。
- 同じKWJA 2.5.1、word tiny、CPU、4 threads、既存cache、offline設定を使う。公式CLIの一括ファイル入力を一度実行し、`--word-batch-size 4` とする。これは一括処理の成立を測る固定値で、最適値探索はしない。
- 起動込み180秒、親子processのRSS最大観測値10GiBを上限とする。現在の16GiB環境内で計測を終えるための作業予算であり、製品の必要メモリではない。新モデル・依存の取得、上流コードの書換えは行わない。
- 全33文書のID・本文・文／形態素index・位置を照合し、保存済みの主辞・格・関係の両端と比較キーを比較する。相違は隠さず記録する。実装の都合で異なる出力を同じと扱う正規化規則は足さない。
- 起動を含むCLI総時間、保存出力の読取り時間、RSS、文書／文字／形態素数を残す。測れない起動と推論の内訳は推定で分離しない。Juman++を再実行しないため、その時間を含む参照構築全体のスループットとは呼ばない。

実装はscratchに限り、既存の読取り・位置対応を再利用する。fresh contextレビュー後に実行し、出力は別に保存する。全33文書の接続が保持され、時間と容量が分かれば、この計測を終了する。差があれば公開処理のどの段階で生じたかを確認し、別モデルの試行へ広げない。計測だけで未知入力の検出精度や全量処理の採用を決めない。
