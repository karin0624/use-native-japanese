# 語の使い方に対応する限定照合

2026年10月22日。計画と実施結果。[旧4入力の検証](minimal-validation.md)で未確認だった対象適合と比較単位を見直した。さらに、述語句全体の一致を要求していた条件を撤回し、語の正規化と格の扱いを分けた。固定入力と参照は維持している。製品の対象をこの二入力へ縮める計画ではない。

## この工程で判断すること

人間が相手語への述語選択を訂正した具体例について、原語の使用実績と訂正語の使用実績を混ぜず、既存解析の値から引用と原位置へ接続できるかを確認する。結果によって、未知入力へ範囲を広げるか、資料・比較条件・解析・接続のどこへ戻るかを決める。全文の検出精度や指摘負担は次の工程で扱う。

比較の核は語彙単位とその結び付きであり、句全体の修飾一致ではない。[Parkほか2016](https://doi.org/10.1016/j.heliyon.2016.e00189)の単純な名詞–格–動詞についての議論と、[公開解析値の調査](parser-investigation.md)を接続する。

必要な処理は次の二つであり、一つの文字列一致へまとめない。

1. **語を正規化する。** 原の動詞を既存の形態素解析が返す基本形・代表表記で照合する。「つける」「つけています」は同じ動詞の用例である。相や丁寧さを含む句全体の一致は要求せず、別動詞の用例へ置き換えない。相手の名詞も既存解析の語彙単位で読む。
2. **同じ出現の格関係を読む。** 述語と相手語の結び付きを既存の格解析・述語項構造解析で取得し、原文に現れた助詞とは分けて扱う。格と表層の記法の対応は、動詞の正規化とは別の処理である。「も」を無条件で「を」へ変換するような規則は書かない。

原文、語・述語句・助詞の表層、各位置、解析器の元の値は引用と確認のために残す。保存する情報を全て照合条件にする必要はない。全複合述語の単一ID、語義分類、二段階の支持判定機構を、この限定照合の前提へ加えない。必要な情報を取得できない箇所は未処理として残し、例文別の構文補修を行わない。

旧案はKNPの `用言代表表記` 全体を一致条件にしたため、既存出力が同じ主辞基本形を返している「畳む／畳んでいる」まで別条件にしていた。既知の機能不足ではなく、照合設計の不備である。この完全一致を確かめる実験は行わない。表層の `係` と格関係の同一視もやめる。

今回の接続は、**既存Juman++ → KWJA 2.5.1のword tiny → rhoknp**を選ぶ。Juman++形式を入力する公式経路では、文字訂正・char・seq2seqの各モデルが不要で、原の表層を保持しながら基本形・代表表記と格関係を得られる。KNP係り受けモードには表層に隠れた格の出力がなく、格解析への切替には追加辞書と既存実測上の費用があるため、必要情報を一緒に返す経路を使う。KNPとの二重解析は行わない。公開仕様・保守状況・依存条件は[解析部品の調査](parser-investigation.md#今回の限定照合で使う経路)に記す。

正規化値はJuman++の公開lemma/canonを用いる。KWJAの `pas.predicate.base_phrase.head` と、`pas.get_all_arguments(relax=False)` の項基本句のheadを、同じ文・形態素indexの入力形態素へ対応付ける。両出力の全文・文境界・全形態素の表層とspanが一致することを確認したうえで、両端のJuman++のcanonと `Argument.case` を照合値にする。全箇所で同じ供給元を使い、欠損時だけ値を切り替えるfallbackにはしない。正規化・格の推測規則は追加しない。

各基本句全体とKWJAの元の値も記録する。本文外の項を本文中の用例に数えず、共参照先を検索対象へ広げない。主辞をあらゆる複合名詞・複合述語の完全なIDとはしない。原文位置との接続と使用実績の照合が今回の確認対象であり、正規化機能の存在を確かめ直すための追加実験は行わない。旧probeは実行しない。

## 結果から次の判断へ

初回の33文書処理は129.64秒で終了した。KWJAのword単独経路が読み・活用を再予測するため、E1/C1の対象主辞ではKWJA側のcanonが欠けた。入力Juman++には正規化値が残っていた。返却された32文書すべてで、Juman++からKWJAへの文境界・形態素数・表層・index・spanの一致を確認したため、上記の供給元分離へ接続仕様を修正する。保存済み出力の読取りだけを改め、解析は繰り返さない。

この対応確認と原文位置の成立は別である。初回は24文書で原文位置の契約が成立し、8文書で原文との差、1文書でKWJA内部のIndexErrorによる出力欠落があった。これらを未観測に置き換えず残す。正規化値の供給元を変えることで位置問題や解析失敗が直ったとはしない。

- **原語と訂正語の支持が分かれる：** 引用の原語・相手語・結び付きと入力位置を確認できれば、この具体例で必要な差を保持できたとする。未知入力・全文へ範囲を広げる計画へ進む。未観測だけで誤用を認定しない。
- **双方が未観測：** 選択した参照の原文と公開値を読む。同じ用法自体がない、用法はあるが比較値が違う、公開解析が別の関係を返す、接続が値を失う、のどれが観測されたかを確認する。独立正用があることだけで参照不足と決めない。
- **原語にも一致用例がある：** 引用が該当する使用実績かを原文で確認する。実績があるなら、この人間訂正例が「用例に裏付けられない使い方」の対照になるかを再考する。今回対象外の正用間の意味差を検出する機能は足さない。
- **関係や位置を失う：** 既存解析の出力と接続結果を照合し、比較設計の不足と実装の不一致を分ける。用例方式全体の否定や別モデルの追加へ飛ばない。

固定入力と選択参照を一度照合し、上のどの判断に進むかを根拠付きで決めれば終了する。結果を見て例を差し替えず、対策をその場で追加しない。実装前のfresh contextレビューでは対象適合と判断の飛躍を点検し、実装後は別のfresh contextレビューで単純さ・既存API利用・不要なテストを確認する。

未知入力の全文検出、名詞未収録への対応、訂正案、Unicode・Markdown全般、実利用速度・容量、辞書・モデルの配布条件は後続工程に残る。この検証を通過しても製品の完成とはしない。

## 実施結果と次に直す接続

全33文書を一周解析し、正規化値の供給元を修正した後は保存出力だけを読み直した。C1の「ネックレスをつけています」と、参照 `1585015#24` の「真珠のネックレスもつける」が `付ける/つける — ヲ — ネックレス/ねっくれす` で一致した。前者の名詞位置は `[37,42)`、述語は `[43,46)`、参照側はそれぞれ `[30,35)`、`[36,39)`。既存の正規化値と格関係を別々に読めば、相・丁寧さ・表層助詞の文字列一致を要求せず、この使用実績と原位置へ接続できる。

E1は原の `着る/きる` を保持し、処理済み参照22段落には一致しなかった。ただし未処理参照9段落があるため、全31段落での未観測とは判定していない。同一キーの取得と解析関係の正しさも区別する。C1には機械的には3出現が一致し、そのうち1出現は括弧内の述語と外側の名詞を解析器が結んだものだった。原文と関係の両端を保存し、一致件数だけで全引用の妥当性や検出性能を認定しない。

未処理の原因を、比較方式の不足とは分けて確認した。

- **8件の位置差：** 既定の文分割・文連結でLF14文字、ASCII空白2文字、全角空白1文字が落ちていた。解析文に対するspanを、元原文の座標として直接使った接続の不足である。次は標準ライブラリdifflibの一致区間を使う文字位置対応を検討し、原文を変更せず、順序・文字被覆・参加語の厳密なslice一致を確認する。保存出力を再利用でき、新しい解析は不要である。
- **1件の出力欠落：** `1095193#21` の文頭 `#` をrhoknpのraw factoryがコメントと解釈し、本文135文字が形態素列から失われた。その空文に対するindex参照がKWJA入力準備中のIndexErrorを起こした。次はliteralな本文と行形式メタデータを分ける構築経路を、既存の文分割規則を変更せず検討する。空文の削除だけでは本文欠落は直らない。接続方法を決める前に再推論しない。

この二点は別の入出力契約であり、語の正規化や用例方式そのものの難しさへまとめない。まず工程2で接続の変更範囲を決め、既存出力で確かめられる部分と、再解析が必要な部分を分ける。全量処理・別モデル・警告分類の追加へは進まない。

位置の接続については、次の範囲を工程3として実施する。Python標準の `difflib.SequenceMatcher(autojunk=False)` が返す一致区間から、解析座標を原文座標へ対応付ける。解析文字の全被覆・同じ順序・原文側の未対応部分が空白だけであることを確認し、非空白本文の欠落は受け入れない。形態素の原文区間を保存し、その区間の文字列が表層と一致することを検査する。隙間をまたぐ範囲は区間列として保持し、間の文字を誤り範囲へ含めない。解析器のspanと原文のspanは別項目にする。

保存済み32出力を読み、既に位置が成立していた24件の根拠と照合値を維持したまま、8件について原文位置を返せるかを確認する。入力二件・参照31件・元注釈は変更しない。本文欠落一件は未処理のまま残す。解析の再実行、原文の書換え、追加の言語規則は不要である。新しい位置付きの成果物を別ファイルへ保存し、旧結果を上書きしない。本文とメタデータの構築境界は、これと独立して工程2で最小の既存機能の拡張を決める。

実行は起動込み129.637秒、C1の起動済み1要求は0.691秒、親子processのRSS最大観測値は約1.86GBだった。C1一件の時間を一般的な応答保証とはしない。依存・モデル・成果物の追加展開は約1.23GB。GPT-6.1-solの実装担当とは別のfresh reviewerが、既存API利用・単純さ・不要なテスト・未処理の扱いを確認した。

元データ、全解析値、引用、位置、版・hash、レビューはGit外の `/workspace/scratch/normalized-usage-probe-20261022/report.md`、原因の根拠は `/workspace/scratch/normalized-usage-position-causes-20261022.md` に保存している。少数例の接続確認を汎用的な誤用検出の完成とはしない。
